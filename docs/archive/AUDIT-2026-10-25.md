# Audyt po PR #5

Zakres: commit `17ae2f7f22f0af09b5965164f58eda39644531cc`, wszystkie pliki repozytorium. Bez uruchamiania produkcyjnego skanera, zapisu do backendu, zmian sekretów i scalania PR. Kod pobrany przez GitHub API; git clone nie działał z powodu niedostępnego proxy środowiska.

## Potwierdzone regresjami i poprawione

1. **Wysoki: odczyty ISBN ignorowały 403/429.** `readSourceHtml` poprawnie zwracał `retryable`, `retryAfter`, `blocked:false`, lecz `bestEffort` z PR #5 traktował te odpowiedzi jako opcjonalną awarię i kontynuował kolejne żądania. Nowy test najpierw wykazał brak oczekiwanego odrzucenia dla obu statusów. Teraz 403/429 zawsze przerywają wzbogacanie, a runner przekazuje błąd i cooldown backendowi bez przesuwania checkpointu. CAPTCHA nadal zatrzymuje źródło. To nie dodaje żadnego obchodzenia limitów.
2. **Średni: skaner był wykluczony z harmonogramu pięciominutowego.** Co pięć minut uruchamiał się wyłącznie matching; skan miał :17 oraz recovery :47 i kontynuacje. Teraz pięciominutowe uruchomienie skanera używa `resumeOnly`, więc wznawia istniejącą kolejkę i nie tworzy pełnego skanu co pięć minut. Dotychczasowe inicjowanie i recovery pozostają. Osobne concurrency z `cancel-in-progress:false` chronią trwające przebiegi. GitHub może opóźniać lub pomijać zaplanowane uruchomienia; cron nie daje gwarancji czasu rzeczywistego.
3. **Średni: CI pomijało większość testów.** Uruchamiało tylko `scanner-reliability.test.mjs`; teraz uruchamia `node --test`, a filtr obejmuje oba workflow.

4. **Średni: błędna klasyfikacja transportu.** Błąd `fetch failed` i HTTP 429 feedu trafiały do kategorii blocked. Teraz są temporary, bez osłabienia jawnej blokady CAPTCHA.

## Potwierdzone zachowanie

- PR #5 zachowuje wszystkie oferty przy timeoutach opcjonalnego odczytu ISBN; nie dopisuje fikcyjnego ISBN. Regresja potwierdza to na trzech ofertach.
- Testy runnera sprawdzają offset wznowienia, reset po zmianie digestu, retry niepewnego zapisu z identycznym `requestId` i treścią, zakończenie po utracie lease oraz przekazanie 429 z Retry-After=180 bez zatwierdzenia partii.
- Worker dopasowania korzysta tylko ze `status` i `process`, opróżnia kolejne partie, kończy dla pauzy i pustej/opóźnionej kolejki. Nie korzysta z transportu marketplace.
- Istniejące testy obejmują walidację hostów, przekierowań i DNS feedu, zmiany HTML, CAPTCHA, statusy 403/429, paginację Vinted/OLX/Allegro Lokalnie, RSS Sprzedajemy.pl, ISBN, deduplikację oraz import feedu powyżej 20 ofert.
- Zapisy ofert następują przed lokalnym przesunięciem offsetu. Niepewny zapis nie jest zgłaszany jako błędne zadanie, które należałoby odtworzyć od zera.

## Potencjalne zagrożenia i granice weryfikacji

- **Backend poza repozytorium:** atomowość ofert, checkpointu i enqueue matching, idempotencja `requestId`, globalna deduplikacja oraz odzyskanie wygasłych lease nie mogą być potwierdzone testami tego kodu. Jeżeli zapis oferty i enqueue nie są jedną transakcją lub nie istnieje reconciliation, oferta może zostać trwale zapisana bez dopasowania. Worker naprawia zaległą kolejkę, ale nie odtwarza brakujących wpisów kolejki. W backendzie potrzebne testy awarii pomiędzy zapisem i enqueue oraz przerwania procesu po claim.
- **Status workera:** jeżeli backend zwraca `processing:0` mimo osieroconych/retry-delayed rekordów albo ignoruje je w claim, worker kończy bez ich odzyskania. Potrzebne kontraktowe testy backendu i sprawdzenie uprawnień OIDC dla joba matching. Sukces joba skanera nie dowodzi działania matching.
- **Ponowienie ISBN:** opis „wymagane ponowne sprawdzenie” jest tekstem; repozytorium nie posiada trwałej kolejki ponownych odczytów ISBN. Oferta trafia do importu bez ISBN, lecz późniejsze wzbogacenie nie jest gwarantowane.
- **Zmiany strony:** digest/offset ograniczają straty, ale przesunięcia ofert pomiędzy stronami podczas skanu mogą powodować pominięcia. Nieznana paginacja kończy zakres jako niepełny. RSS i stare zadania bez paginacji mają świadomy limit 20; JSON maksymalnie 1000. To ograniczenia pokrycia, nie dowód utraty zatwierdzonych ofert.
- **Deduplikacja:** marketplace normalizuje query/hash, lecz alias hosta i zmiana sluga tego samego ID Vinted mogą dać różne URL. Ostateczna deduplikacja musi bazować na tożsamości źródła w backendzie.
- **Budżet i payload:** limit partii liczony jest przed wzbogaceniem ISBN, według długości stringa, nie bajtów. Skrajnie duże opisy lub szczegóły mogą przekroczyć limit API; potrzebny znany kontrakt rozmiaru i test graniczny backendu. Jeden retry zapisu może przekroczyć pozostały budżet pętli; twarde przerwanie Actions wymaga odzyskania lease po stronie backendu.
- **Transport poprawiony:** `fetch failed` oraz HTTP 429 z feedu są klasyfikowane jako przejściowe; jawne `blocked` ma pierwszeństwo. Nowe testy runnera wstrzykują oba błędy i sprawdzają brak zatwierdzenia partii oraz zachowanie cooldownu.
- **Testy przerwania:** test utraty lease i niepewnego zapisu używa atrap. Nie symuluje SIGKILL wraz z rzeczywistym D1 ani odtworzenia transakcji. Nie wykonano testów live HTML ani produkcyjnych żądań.
